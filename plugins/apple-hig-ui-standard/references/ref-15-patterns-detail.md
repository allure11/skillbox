# 模式细则（Patterns · 补充篇）

> 来源：Apple HIG《模式》。本篇补充 `ref-08-patterns.md` 之外的 22 个模式；
> 模态化（Modality）见 `ref-08`，反馈与加载见 `ref-07`。

## 一、搜索（Searching）【强制】

### 最佳实践
1. **如果搜索很重要，请将其放在 App 或视图中的主要位置**【强制】
   （如「备忘录」放在底部工具栏；「照片」「Apple TV」用**专用标签页**）。
2. **力求通过单个位置让 App 内容可供搜索**【强制】——
   用户希望通过**一个清晰易辨的位置**查找任何内容；
   版块划分明确的 App 提供**局部搜索**仍可能有用（如 iOS「音乐」中搜索用作当前视图的过滤器）。
3. **明确显示当前的搜索范围**【强制】——用描述性占位符文本、**范围栏**或标题强化；
   如「邮件」中始终有用户所搜索邮箱的明确参考。
4. **提供让搜索更简单的建议**——开始键入前显示最近搜索项，或随键入提供预测建议。
5. **显示搜索历史记录前，考虑用户隐私**【强制】——
   用户可能不希望搜索历史出现在他人可能看到的地方；
   **如要显示，必须提供按需清除历史记录的方式**。

### 系统级搜索（iOS/iPadOS/macOS）
- **让 App 内容在「聚焦」中可供搜索**——使内容可索引并指定**元数据**描述性属性；
  「聚焦」会提取、储存并整理此类信息以实现快速全面的搜索。
- **定义所处理自定义文件类型的元数据**（提供「聚焦」文件导入程序插件）。
- **使用「聚焦」在 App 环境中提供高级的文件搜索功能**。
- **优先采用系统提供的打开和保存视图**（通常包括内建搜索栏，可搜索和过滤整个系统）。
- **如果 App 生成自定义文件类型，请采用「快速查看」生成器。**

## 二、设置（Settings）【强制】

### 最佳实践
1. **尽量提供可为最广泛用户带来最佳体验的默认设置**【强制】——
   如针对设备自动实现性能最大化，而非要求玩家做选择；**用户可能无需任何调整即可开始享受。**
2. **尽量减少提供的设置数量**【强制】——过多设置会让体验不够友好，且很难找到特定设置。
3. **按用户期望的方式提供设置**【强制】——实体键盘连接时用户通常用 **Command-逗号（,）**；
   游戏中玩家通常用 **Esc**。
4. **避免使用设置来要求提供可通过其他方式获得的信息**【强制】——
   游戏可**自动检测**所连接的控制器或配件；App 可检测用户当前是否在使用深色模式。
5. **遵从用户针对整个系统范围的设置，避免在自定义设置区域中包括重复版本**【强制】——
   用户期望用系统「设置」管理全局选项（无障碍调节、滚动行为、认证方法），
   并希望所有 App 遵守这些选择；**包括全局选项的自定义版本会让人误以为全局设置不适用于你的 App。**

### 设置分类
- **通用设置**：将**通用、不常更改**的设置放在自定义设置区域中
  （用户必须中止当前操作才能打开设置区域）。
- **任务特定选项**【强制】：**如果可能，首选让用户无需前往设置区域即可修改任务特定的选项**——
  将调整视图、重新排列项目、过滤列表等选项**放在其影响的屏幕上**；
  放在单独的设置区域会**让其失去与上下文的联系**，且通常在用户继续任务时才显示结果。
- **系统设置**：**仅将极少更改的选项添加到系统提供的「设置」App 中**；
  合理时考虑提供可直接从界面打开「设置」App 的按钮。

### 平台差异
- **macOS**：
  1. **将设置项包括在 App 菜单中**【强制】——**避免将设置按钮添加到窗口工具栏**
     （会挤压用户常用基本命令的可用空间）；提供文稿级选项则添加到「文件」菜单。
  2. **调暗设置窗口的最小化和最大化按钮**——Command-逗号可快速打开，无需放程序坞，
     且设置窗口可完全容纳当前面板，用户不需要展开窗口。
  3. **使用一直可见且始终指示活跃工具栏按钮的非可自定义工具栏。**
  4. **更新窗口标题以反映当前可见的面板**（不含多面板时可用「*App 名称*设置」）。
  5. **恢复最近查看的面板。**
- **watchOS**：**不会将自定义设置添加到系统「设置」App**——
  考虑将**少量基本选项放在主视图底部**，或让用户使用「更多」菜单重新配置对象。

## 三、用户引导（Onboarding）【强制】

**理想情况下用户只需通过体验即可理解 App**；确需引导时，设计**快速且有趣的可选流程**。
用户引导在**启动完成后**出现，**不属于启动体验**。

### 最佳实践
1. **通过交互进行指导**【强制】——用户可实际执行所学任务时能更好地掌握和记住；
   尽可能提供**交互式引导**，让用户可安全测试操作、探索功能或尝试游戏机制。
2. **考虑提供一系列环境特定提示，而非单一引导流程**【强制】——
   环境相关提示帮助用户在取得进展时了解当前任务，
   让用户**专注于单个操作或任务**直到接触新信息；
   **当指导性内容引用界面特定区域时，在该区域附近显示这些说明。**
3. **如需展示必要的引导流程，设计简要有趣且无需记忆大量信息的体验**【强制】——
   内容过多会让用户不知所措且记不住。
4. **如有必要提供单独的教程，考虑将其作为可选内容**【强制】——
   首次启动可跳过时，**不要让它在之后启动时再次出现**，
   但**确保用户以后想查看时可轻松找到**（放在帮助、账户或设置区域）。
5. **让引导内容专注于你提供的体验**【强制】——用户进入引导是为了解你的 App，
   而非学习如何使用系统或设备。

### 其他内容
- **如有必要使用启动画面，请简要显示**——设计简洁传达信息的精美图形，时长恰到好处。
- **避免让大量下载妨碍用户引导**——考虑在软件包中包括足量媒体及内容。
- **避免在引导流程内显示许可条款详细信息**——让 App Store 显示。

### 其他请求【强制】
1. **推迟不必要的设置流程或自定义步骤**【强制】——提供合理默认设置，
   让大多数用户可立即开始交互而无需额外配置。
2. **如果 App 需要访问隐私数据或资源才可工作，考虑将许可请求整合到引导流程中**——
   此时可向用户展示**为什么需要许可以及许可后的益处**；
   否则在用户首次访问依赖隐私数据的功能时显示请求。
3. **优先让用户先体验 App 或游戏，再提示其评分或购买。**

## 四、数据输入（Entering Data）【强制】

改进数据输入体验的两个方向：**预收集尽可能多的信息以减少用户需提供的量**；
**支持所有可用的输入方式让用户选择适合自己的一种**。

### 最佳实践
1. **尽可能从系统获取信息**【强制】——不要让用户输入可自动收集的信息
   （如从设置收集，或经许可收集的位置、日历信息）。
2. **明确你需要的数据**——在文本栏中显示提示（`username@company.com`）或介绍标签（「电子邮件」）；
   **用合理的默认值预填充栏位**，可最大限度减少决策并加速输入。
3. **适当时使用安全文本输入栏**——敏感数据须遮盖输入（每字符显示小实心圆圈）；
   visionOS 中使用系统提供的文本栏时，系统只向佩戴者显示输入数据；
   使用隔空播放流播放时**安全文本栏会自动模糊**。
4. **切勿预填充密码栏**【强制】——始终要求用户输入，或使用生物识别/钥匙串认证。
5. **在可能时提供选项，而不是要求输入文本**【强制】——
   从选项列表选择通常比键入更轻松高效，**即使有方便可用的键盘时也是如此**；
   考虑用选择器、菜单或其他选择组件。
6. **尽可能让用户通过拖放或粘贴方式提供数据。**
7. **动态验证栏位值**【强制】——用户在填写冗长表单后需返回改正错误会特别懊恼；
   用户输入后立即验证并即刻反馈，让用户有机会立即改正；
   数字数据可考虑用**数字格式化程序**（仅接受数字值，可按特定方式显示小数位、百分比、货币）。
8. **输入数据为必要条件时，确保用户了解必须提供后才能继续**【强制】——
   **仅在用户输入必填数据后才将「下一步」「继续」按钮变为可用。**

### 平台差异
- **macOS**：**考虑使用扩展工具提示在栏位中显示被裁剪或截断文本的完整版本**
  （指针停留在栏位上时显示）。
- 其余平台无额外考量。

## 五、管理账户（Managing Accounts）【强制】

**仅在你的核心功能需要时才请求用户创建账户**，否则让用户无需账户也可享受 App；
需要账户时考虑使用「**通过 Apple 登录**」。

### 最佳实践【强制】
1. **解释创建账户的好处和如何注册**【强制】——编写简短友好的描述说明原因及好处，**在登录视图显示**。
2. **尽可能延迟登录操作**【强制】——
   在执行任何有用操作前被迫登录，用户常常会弃用；应让用户**先有机会感受你的 App**
   （如购物 App 让用户尽情浏览，仅在准备购买时才要求登录）。
3. **优先使用通行密钥（passkeys）**【强制】——
   iOS、iPadOS、macOS、visionOS App 中未使用「通过 Apple 登录」时，
   应优先用通行密钥（用户创建或登录只需提供用户名）；
   继续用密码认证则**要求双重认证**。
4. **始终标识你提供的认证方式**【强制】——
   用「通过面容 ID 登录」而非宽泛的「登录」。
5. **仅提及在当前环境中可用的认证方式**【强制】——
   不要在不提供面容 ID 的设备上提及面容 ID；检查设备功能并使用适当术语。
6. **通常应避免提供选择使用生物识别认证的 App 特定设置**【强制】——
   用户在系统层面打开，App 内设置非常多余且可能造成混淆。
7. **避免使用术语「密码」来指代账户认证**【强制】——
   用户创建密码用于解锁设备或认证 Apple 设备；
   在界面中使用该术语会让用户以为你要其重复使用设备密码。

### 删除账户【强制】
> 若帮助用户在 App 内创建了账户，**还必须帮助其删除账户，而非仅停用账户**；
> 同时须了解并遵守所在地区与账户删除和被遗忘权相关的法律规定。

1. **在 App 内提供发起账户删除的明确方式**【强制】——
   无法在 App 内删除时，**必须提供可执行此操作的网页的直接链接**；
   **放在易于发现的位置**，不要深藏在隐私政策或服务条款页面中。
2. **无论用户在 App 内还是网站上执行删除，应提供一致的体验**——
   避免其中一个流程更长或更复杂。
3. **考虑让用户计划未来删除账户**（提供计划删除时须同时提供立即删除选项）。
4. **告知用户账户删除何时会完成，并在完成后通知用户。**
5. **如果支持 App 内购买，应帮助用户了解删除账户时会如何处理付款和取消**：
   - 可自动续期的订阅**会在用户取消订阅前继续通过 Apple 付款**，无论是否删除账户；
   - 删除账户后，用户**需要取消订阅或请求退款**。
   - 并提供信息描述如何取消订阅和管理购买项。
6. 使用「通过 Apple 登录」创建账户时，**用户删除账户时须撤销关联的令牌**。

### 电视提供商账户
- 用户已在系统层面登录时，**避免显示退出登录选项**。
- **勿指示用户通过调整隐私控制来退出登录**【强制】——
  「设置」>「隐私」中的电视提供商控制并非退出登录机制。

### 平台差异
- **tvOS**：大多数用户使用遥控器而非键盘，**仅请求必要的最少量信息**；
  **优先让用户使用另一台设备注册或认证**；
  **用户已登录共享账户时，避免每次其成为当前用户时都请求选取个人资料**；
  **尽量减少数据输入**（需要电子邮件时显示电子邮件键盘屏幕，含最近输入的地址列表）。
- **watchOS**：使用 iCloud 同步提供钥匙串访问许可，让用户自动填充用户名密码并保留 App 设置。

## 六、管理通知（Managing Notifications）【强制】

> 发送任何通知前**需要获得许可**；用户可在设置中更改此决定或静音所有通知（部分地区的政府警报除外）。

### 中断级别【强制】
系统为非通信通知定义了**四个中断级别**，必须为每条非通信通知指定：

| 中断级别 | 说明 | 覆盖定时推送 | 绕过专注模式 | 覆盖响铃/静音开关 |
|---|---|---|---|---|
| **被动** | 用户可在有空时查看（餐厅推荐） | 否 | 否 | 否 |
| **主动**（默认） | 用户可能希望送达时立即知晓（比分更新） | 否 | 否 | 否 |
| **即时** | 直接影响用户并需要立即注意（账户安全、快递派送） | **是** | **是** | 否 |
| **重要** | 与健康和安全相关的紧急信息；**极其少见**，通常来自政府和公共机构 | **是** | **是** | **是** |

- ⚠️ **重要通知可覆盖响铃/静音开关并绕过定时推送和专注模式，必须获得授权才能发送。**
- 专注模式可帮助用户在为睡眠、工作、阅读或驾驶预留的时间段内过滤通知；推送定时可让用户选择立即接收还是摘要接收。
  **即使专注模式可能延迟推送提醒，通知本身在送达时就立即可用。**

### 最佳实践【强制】
1. **通过准确呈现每条通知的紧急程度来构建信任**【强制】——
   用户有多种方式调整接收方式（包括关闭所有通知），因此**分配中断级别时必须尽可能实事求是**；
   不应让用户感到被高紧急度的低优先级信息打断。
2. **仅为与当下相关的通知使用「即时」中断级别**【强制】——
   确保通知关于**现在正在发生或一小时内将会发生**的事件；
   即时通知首次送达时系统会描述其工作原理，并提供关闭方式；
   之后系统会定期提供机会评估你的即时通知使用效果。

### 发送营销通知【强制】
1. **不要使用通知发送营销或推广内容，除非用户明确同意接收。**
2. **勿使用「即时」中断级别发送营销通知**【强制】——
   营销通知**绝不能绕过专注模式或定时推送设置**。
3. **想发送推广或营销通知应获得许可**——用提醒、模态视图或其他界面描述要发送的通知类型，
   并提供明确的接收或不接收方式。
4. **确保用户可在 App 内管理其通知设置**【强制】——
   除请求许可外，**必须提供 App 内设置屏幕让用户更改选择**。

### 平台差异
- iPhone 上 App 的通知设置**默认应用到 Apple Watch 上的相同 App**；
  用户可在 iPhone 的 Apple Watch App 中管理，也可在 Apple Watch 收到通知时**向左轻扫**单独设置选项
  （「1 小时不再提醒」「关闭即时通知」）。

## 七、撤销和重做（Undo and Redo）

用户期望撤销和重做能反转最近的操作；因内容更改前用户常会多次尝试撤销，
**帮用户预测撤销/重做的结果并突显相关结果至关重要**。

### 最佳实践【强制】
1. **尽量帮助用户预测撤销和重做的结果**【强制】——
   摇动 iPhone 时可显示描述对应结果的提醒让用户选择；
   提供菜单项时可修改标签标明结果（「撤销键入」「重做粗体」）。
2. **显示撤销或重做的结果**【强制】——
   用户想撤销的最近操作可能影响**不再可见的内容或区域**；
   此时须突显每次结果，避免用户误以为没有任何影响而**重复操作**
   （如滚动文稿以显示被恢复的段落）。
3. **允许用户多次撤销**【强制】——
   **避免为用户可撤销或重做的次数设置不必要的限制**；
   用户在打开文稿、保存工作等逻辑步骤后通常期望能撤销所执行的**每一项**操作。
4. **考虑允许用户一次复原多项更改**（对单个属性的增量调整；或轻松撤销自打开/保存以来的所有更改）。
5. **仅在需要时提供撤销和重做按钮**——用户通常期望系统提供的方式
   （macOS「编辑」菜单、键盘快捷键、摇动 iPhone）；
   有必要提供专门按钮时**使用系统提供的标准符号**并**放在工具栏中**。

### 平台差异
- **iOS、iPadOS**：
  1. **避免重新定义撤销和重做的标准手势**【强制】（三指轻扫、摇动 iPhone）。
  2. **简洁准确地描述要撤销或重做的操作**——
     提醒标题会自动包括「撤销 」或「重做 」前缀（含尾部空格），
     你需额外提供**一两个**显示在该前缀之后的词（如「撤销命名」「重做地址更改」）。
- **macOS**：
  1. **将撤销和重做命令放在「编辑」菜单中并支持标准键盘快捷键**【强制】——
     Mac 用户期望在「编辑」菜单**顶部**找到，并分别使用 **Command–Z** 和 **Shift–Command–Z**。
- **tvOS、watchOS**：**不支持**。**visionOS**：无额外考量。

## 八、启动（Launching）【强制】

启动在用户打开 App 时开始（包括初始下载），**在首屏就绪时结束**；
启动完成后可提供用户引导体验。

### 最佳实践【强制】
1. **立即启动**【强制】——用户希望可立即开始交互，**有时甚至几秒钟都不想等待**。
2. **按照平台需要提供启动屏幕**——iOS、iPadOS、tvOS 系统会显示启动屏幕后迅速替换为首屏；
   **macOS、visionOS、watchOS 不需要启动屏幕**。
3. **如果需要启动画面，考虑在用户引导流程开始时显示**（不提供引导时可在启动完成时立即显示）。
4. **App 重新启动后恢复之前的状态，以便用户可以从离开的位置继续**【强制】——
   避免让用户回溯步骤；**尽可能恢复之前状态的细枝末节**——
   将视图滚动到用户最近查看的位置，显示与离开时**相同状态和位置**的窗口。

### 启动屏幕（不适用于 macOS、visionOS、watchOS）【强制】
1. **淡化启动体验**【强制】——启动屏幕**不属于引导体验或启动画面，也不用于艺术表达**；
   唯一功能在于**增强对「快速启动且立即可用」这种体验的感知**。
2. **设计与 App 或游戏首屏几乎相同的启动屏幕**【强制】——
   加入不协调元素会产生不愉快观感；首屏前显示纯色则创建只显示该纯色的启动屏幕；
   并**确保启动屏幕匹配设备的当前方向和外观模式**。
3. **避免在启动屏幕中包含文本，即使首屏显示文本**【强制】——
   启动屏幕内容不会改变，**任何文本都不会被本地化**。
4. **不打广告**【强制】——不用于品牌宣传；
   避免创建看起来像启动画面或「关于」窗口的屏幕，不包含标志或其他品牌元素
   （除非它们是 App 首屏的固定部分）。

### 平台差异
- **iOS、iPadOS**：**以适当的方向启动**——同时支持竖排横排时按设备当前方向启动；
  界面只在一个方向运行时按该方向启动并让用户按需旋转设备；
  **确保只能横排显示的界面在用户向左或向右旋转时都能正确响应**。
- **tvOS**：⚠️ **启动屏幕是静态的**（与 tvOS App 中随处可见的分层图像不同）；
  **直播观看 App 中，考虑在用户启动后立即自动开始播放**
  （不妨在不活跃几秒钟后便开始播放新的或最近观看过的直播内容）。
- **visionOS**：**即使 App 为全沉浸式，也考虑在共享空间中启动**——
  在共享空间打开窗口可在加载时提供更多相关使用环境，并呈现供用户打开全沉浸式体验的控制；
  **用户希望能选择何时转换到全空间**（尤其当前正在共享空间运行其他 App 时）。
- **macOS、watchOS**：无额外考量。

## 九、拖放（Drag and Drop）

> 拖放需要**源位置**与**目的位置**。一般规则：放入**同一容器**执行**移动**；
> 放入**另一容器**执行**拷贝**；**App 间拖放始终执行拷贝**。

### 最佳实践【强制】
1. **App 应尽可能支持拖放**（系统提供的文本栏和文本视图原生支持）。
2. **提供完成拖放操作的备选方法**【强制】——
   用户有时不便或无法执行拖放；可加入用于拷贝并移动到其他位置的菜单命令；
   iOS/iPadOS 中可用无障碍 API 识别源位置和目的位置以支持辅助技术进行拖放。
3. **确定在 App 内拖放内容是移动还是拷贝**【强制】——
   同容器内移动合理，不同容器间拷贝合理；
   **更改默认行为前应考虑大多数用户期望的行为，并首选最不可能导致沮丧或数据丢失的行为**。
4. **合理支持多项目拖放**——
   iPadOS 中用户可选择一个项目、开始拖移，再在不停止拖移的情况下添加其他项目。
5. **优先考虑让用户撤销拖放操作**【强制】——
   用户有时会无意中放到错误位置；
   也可在完成**无法撤销**的拖放前请求确认；
   无法撤销时提供反转结果的方法可能很合理。

### 反馈规则【强制】
1. **用户拖移所选内容约三点时显示拖移图像**【强制】——
   创建**半透明**表示（有助于区分原始内容与表示，并让用户看到目的位置）；
   显示直至用户放置内容。
2. **修改拖移图像以帮助用户清晰预见结果**（如拖照片入文稿时放大到默认大小）；
   也可使用**拖移集群**直观分组多个项目，并在用户放置时取消分组；
   ⚠️ **避免拖移图像持续且大幅变化而造成分散注意力。**
3. **告知用户目的位置是否可接受拖移内容**【强制】——
   接受时显示插入点或高亮标记包含视图；不接受时不显示视觉反馈或明确显示「不允许」图像（`circle.slash`）；
   **仅当内容位于目的位置上方时才显示提示**；有多个可能目的位置时**帮助用户一次识别一个**。
4. **放置失败时提供视觉反馈**（项目移回源位置，或放大并淡出）。

### 接受放置
- **需要时滚动目的位置的内容**（用户在滚动容器内拖移时内容自动滚动；拖出容器外则停止）。
- **当有选择时，选择 App 可接受的放置内容信息最丰富的版本。**
- **如有需要，仅提取放置内容的相关部分**（拖联系人到收件人栏只显示名字和地址）。
- **连接实体键盘后，在放置时检查 Option 键**（按住 Option 拖移可强制同容器内执行拷贝）。
- **放置内容需要时间传输时提供反馈**（进度指示符；集合/列表/表格中在放置位置显示占位符）。
- **当放置内容启动任务或操作时提供反馈**（如放到打印控制上，告知任务已开始并让用户了解进度）。
- **为放置文本应用适当样式**——源和目的都支持同一文本样式时保持原始字体、字样、大小等属性；
  否则应用目的位置的样式。
- **放置后，在目的位置保持内容的选择状态，并按需在源位置更新**【强制】——
  同容器移动则内容从原位置消失；同容器拷贝则取消选择保留在原位置的内容；
  拖到其他容器则取消选择源位置的内容。

### 平台差异
- **iOS、iPadOS**：**让用户执行多个同时进行的拖移活动**
  （iPadOS 中可按顺序把项目添加到正在进行的拖移会话；需支持拖移期间添加项目和接受多个同时放置）。
- **macOS**：
  - **考虑让用户将内容从 App 拖入访达**（以 App 随后能打开的格式呈现，如「日历」用 `.ics`）；
  - **允许用户从非活跃窗口拖移所选内容而无需先激活该窗口**（后台所选内容）；
  - **尽可能让用户从非活跃窗口拖移单个项目而不影响现有的后台所选内容**；
  - **考虑在多项目拖移操作期间显示标记**（含数字的实心小椭圆指示拖移数量；目的位置只接受子集时更新数量）；
  - **考虑更改指针外观以指示放置时会执行的操作**（拷贝指针、拖移链接、项目消失、不允许操作）；
  - **尽可能让用户通过一个动作来选择和拖移内容**（除非要选多个项目）。
- **visionOS**：**如果可能，启动你的 App 以处理用户放入空白空间的内容**
  （放置 URL 时 Safari 启动；放置支持「快速查看」的内容时「快速查看」启动）。
- **tvOS、watchOS**：**不支持**。

## 十、文件管理（File Management）

> **创建与打开**：提供「新建」「打开」等命令，在 iPadOS 快捷键界面 / macOS「文件」菜单中显示；
> **无论键盘快捷键是否可用，都包括添加（+）按钮**。
> 自定义文件浏览器时**支持用户对平台文件系统的理解**（显示「文稿」、iCloud 文件夹或最近位置）。

### 保存工作【强制】
1. **帮助用户确信其工作始终会被保存，除非选择取消或删除**【强制】——
   **一般来说应避免让用户采取明确操作来保存工作**；
   相反在其编辑、关闭文件或切换到另一个 App 时**自动执行定期保存**。
2. **默认隐藏文件扩展名，但允许用户选择查看**——确保在所有保存或打开界面中反映当前选择。

### 「快速查看」预览
- **即使 App 无法打开文件，也让用户可使用「快速查看」显示窗口进行预览。**
- **如果 App 生成自定义文件类型，考虑实现「快速查看」生成器**（让其他 App、访达、「文件」、「聚焦」显示预览）。

### 平台差异
- **iOS、iPadOS**：
  - **文稿启动器**（iOS 18 / iPadOS 18+）以全屏体验呈现，含三部分：
    **标题卡**（App 标题 + 两个 App 特定按钮）、**背景图像 + 补充图像**、**含文件浏览器的表单**。
    - **将标题卡的按钮分配至 App 的最重要功能**【强制】（主要按钮一般用于创建新文稿，
      次要按钮提供额外选项，如 Numbers 的主要「开始书写」、次要「选取模板」）；
    - **提供与补充图像和标题卡区别显著的背景**，避免复杂图像或图案分散注意力；
    - **注意补充图像的放置**（可放在标题卡前后形成深度，但须确保 App 名称和两个按钮清晰可见；
      避免过多补充图像造成杂乱；在支持的屏幕尺寸和方向下测试）；
    - **有节制地使用动画**（优先柔和、重复性的动画，如轻柔收放或摇摆）。
  - **文件提供程序 App 扩展**：
    - **只显示适合当前上下文的文稿**（PDF 编辑 App 加载扩展时仅列出 PDF）；
    - **导出和移动文稿时让用户选择目的位置**；
    - **避免包含自定义顶部工具栏**【强制】（扩展已加载在含工具栏的模态视图内，第二个工具栏会让人困惑并占用空间）。
- **macOS**：
  - **自定义文件管理**：**除非有重要理由，否则使用默认文件浏览器**；
    让自定义打开界面便于使用（提供「打开最近使用」、过滤标准、一次选多个文稿）；
    可自定义「打开」按钮标题反映任务（如「插入」）；
    提供保存界面让用户更改名称、格式或位置（新文稿标题默认为「未命名」）；
    可扩展「保存」对话框（如「邮件」保存为文件时含「包括附件」选项）。
  - **访达「同步」扩展**：可在访达内显示标记指示同步状态、
    提供自定义关联菜单项（加入个人收藏、添加密码保护）、提供自定义工具栏按钮（启动同步）。
  - **帮助用户避免因关闭自动保存而丢失工作**【强制】——
    用户关闭自动保存后，选择关闭文稿、退出 App、退出登录或重启时**须告知更改尚未保存并显示保存对话框**。
  - **自动保存关闭后，确保用户知道文稿何时有未保存的更改**——
    在文稿窗口关闭按钮上和「窗口」菜单中的文稿名称旁**显示圆点**；
    **自动保存打开后显示圆点会让人困惑**（意味着用户需操作以避免丢失）；
    可给标题追加「已编辑」，但须在自动保存或用户明确保存后移除。
- **tvOS、visionOS、watchOS**：无额外考量（watchOS 和 tvOS 通常不提供文稿浏览界面）。

## 十一、提供触感反馈（Playing Haptics）【强制】

### 最佳实践
1. **根据文档所述的含义来使用系统提供的触感反馈模式**【强制】——
   用户可识别标准触感反馈；**文档所述模式用例不适用时避免将其用于表达其他含义**，
   应改用通用模式或创建自己的模式。
2. **在整个 App 或游戏中使用一致的触感反馈**【强制】——
   须在每个触感反馈及其来源操作之间建立**清晰、具有因果关系的联系**
   （如任务失败的触感模式不能用于通关等积极结果，否则用户会困惑）。
3. **首选将触感反馈用作其他反馈的补充**【强制】——
   视觉、听觉和触觉像在现实世界中般协调时体验更连贯；
   通常让触感反馈与其搭配的动画**在强度和锐度上相匹配**，并可将声音与触感同步。
4. **避免滥用触感反馈**【强制】——
   偶尔出现的触感恰到好处，频繁出现会令人厌倦；
   **最佳触感反馈体验通常可能不会被用户注意到，但在关闭后他们会不习惯。**
5. **在大多数 App 中，首选提供与离散事件互补的短暂触感反馈**——
   伴随游戏流程的持续触感可增强体验，但 **App 中的持续触感会淡化反馈意义并分散注意力**
   （如 Apple Pencil Pro 上连续触感会难以区分书写体验，甚至让手握体验变糟）。
6. **将触感反馈设为可选**【强制】——允许用户关闭或静音，
   并**确保无触感反馈时用户仍可享受 App 或游戏**。
7. **注意提供触感反馈可能会影响其他用户体验**——
   确保振动不干扰涉及相机、陀螺仪或麦克风等设备功能的使用体验。

### 自定义触感反馈
- 两种基础构建块：**瞬态事件**（简短紧凑，像轻敲或脉冲）与**持续事件**（像持续振动）。
- 可控制**锐度**（传达意图：柔软圆润自然 vs 清脆精细机械）与**强度**（力度）。
- 组合瞬态/持续事件 + 调整锐度强度 + 可选音频内容，可创造各式体验。

### 平台差异
- **iOS**（支持的机型）：
  - 标准组件（切换、滑块、选择器）默认提供 Apple 设计的系统触感；
  - 反馈生成器提供三类预定义模式：
    - **通知**：成功（任务已完成）/ 警告（产生某类警告）/ 错误（发生错误）；
    - **冲击**：轻型 / 中型 / 重型 / 刚硬（坚硬非弹性）/ 柔软（柔软弹性）；
    - **选择**：UI 元素的值发生更改。
- **macOS**（配备妙控板时）三种模式：

  | 模式 | 描述 |
  |---|---|
  | **对齐** | 指示拖移项目的对齐状态（绘图 App 中对齐形状、缩放到特定尺寸、触及项目起点/终点或最大/最小范围） |
  | **水平变化** | 指示不连续压力水平之间的活动（快进按钮的播放速度随压力水平变化） |
  | **通用** | 其他模式均不适用时的通用反馈 |

- **watchOS**：Apple Watch Series 4 及后续机型在**数码表冠**上提供触感反馈；
  系统默认提供**线性定位**；某些系统控制（如表格视图）在新项目滚动到屏幕时提供定位。
  watchOS 定义的触感反馈类型：**通知、上升、下降、成功、失败、重试、开始、停止、点击**
  （**通知**：告知用户有重要或异常事件发生，需引起注意；系统在通知到达时提供）。

## 十二、其余模式速查（要点）

| 模式 | 核心要求 |
|---|---|
| **图表化数据** | 保证准确、可读、可访问；**不依赖颜色**传达数据含义；提供无障碍描述 |
| **协作与共享** | 明确权限与可见性；邀请流程简单；参与者身份清晰可辨 |
| **全屏显示** | 进入/退出全屏的方式须明确；保持状态；**提供可靠方法恢复隐藏的界面元素** |
| **实时查看类 App** | 相机、AR 等实时视图上的控件布局不遮挡主体；控制半透明且易触达 |
| **多任务** | 分屏、多窗口、画中画下的**布局与状态适配**；窗口变窄时优先维持布局稳定 |
| **提供帮助** | 帮助入口易发现；**优先提供上下文相关帮助**；macOS/visionOS 可用扩展工具提示 |
| **播放音频** | 播放控制清晰；支持后台播放；正确处理音频打断 |
| **播放视频** | 播放器控件、画中画、字幕与全屏；与「视频」App 整合（tvOS） |
| **打印** | 打印设置与预览流程；提供系统对话框而非自定义 |
| **评分与评论** | **让用户先体验，再提示评分**；请求时机自然、频率克制（避免打断） |
| **体能训练** | watchOS 体能训练类 App 的界面与数据呈现；运动中可读性优先 |
