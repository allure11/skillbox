# 包容性、隐私与从右到左（Inclusion / Privacy / RTL）

> 来源：Apple HIG《包容性》《隐私》《从右到左》。三者为**跨平台通用**规范，无平台差异。

## 一、包容性（Inclusion）

目标是：把用户放在首位，以尊重他人为前提，用**所有用户都能访问和理解**的方式呈现内容与功能。
避免把审查局限于「搜索可能的冒犯性内容」——**无冒犯性内容的 App 不一定具有包容性**。

### 友好用语
- **从不同角度斟酌语气**：学术味十足的语气会让 App 看起来只欢迎高学历用户。
  保持**清晰、直接、尊重他人**。
- **注意提及他人的方式**：用「你 / 你的」直接称呼用户效果最好；
  用「用户 / 玩家」间接提及会产生距离感和冷漠感；「我们 / 我们的」应保留给软件或公司本身。
- **避免未定义的专业/技术术语**：必须使用时**先定义**并使其便于查阅；改用平实语言会让句子更易读、更易翻译。
- **用平实语言替代口语表达**：口语通常有文化特异性、难以翻译，部分短语还具有排斥性含义。
- **谨慎考虑幽默**：幽默高度主观、难以跨文化翻译，可能让用户困惑、恼火或感到冒犯。

### 易于上手
- 呈现**清晰直接的界面**。
- **搭建学习路径**：设计用户引导流程帮助新用户循序渐进，同时让其他用户可直接跳到想要的内容。

### 性别认同
- **避免不必要的性别提及**。例：「你可以让订阅者将他或她的食谱发布到你的共享文件夹」
  → ✅「订阅者可将食谱发布到你的共享文件夹」（同时避免了单数代词，便于本地化）。
- **避免在头像、表情符号、图形或游戏角色中提及特定性别**；需要通用人物时用**无性别图形**
  （`person.crop.circle`、`person.3.fill`、`figure.wave`）。
- 确需性别信息时（健康、法律原因），提供包容性选项：**非二元性别 / 自我认同 / 拒绝声明**，
  并允许用户指定其使用的代词。

### 用户与背景
- **展现人类多样性**：用户在其中认出与自己相似的人时，便不太可能感到被排斥。
- 描述职业或行为时**避免刻板印象**（如只显示男医生、女护士；延续现实刻板印象的英雄与反派）。
- **检查背景与对象**：高富裕程度在某些情况下合理，在其他情况下会显得脱离现实。
  优先使用大多数用户熟悉且相关的地点、家庭、活动与物品。

### 避免刻板印象
- 意识到自身的偏见与概论，识别设计决策在哪里受其影响。
- ⚠️ **典型案例**：账户访问 App 若以「一男一女及其亲生孩子」定义*家庭*，会排斥所有其他家庭形态。
- ⚠️ **案例**：身份确认的安全问题「你大学时最喜欢的科目是什么？」「你的第一辆车是什么牌子？」
  「你第一次看到彩虹时是什么感觉？」——这些都基于**并非人人都有的经历**。
  → ✅ 改用普遍人类经验：「你最喜欢的活动是什么？」「你的第一个朋友叫什么名字？」「什么品质最能描述你？」
- **避免设想，专注于包容性。**

### 无障碍（包容性视角）
- **每种残障都是谱系**（视障从弱视到完全失明，包括色盲、视力模糊、光敏感、周边视力丧失）。
- **每个人都可能经历残障**：除随年龄增长的残障外，还有*暂时性残障*（感染导致的短暂听力损失）
  与*情景性残障*（在嘈杂火车上听不见）。
- **避免使用排斥残障人士的图像和语言**；**书写时以人为本**（先描述成就和目标，再提及残障）。
- **优先考虑简单性和可感知性**：熟悉且一致的交互方式 + 确保每个用户都能通过视觉、听觉或触觉感知内容。

### 语言与本地化
- 用户期望为**文本**选取语言、为**日期/时间/货币**选取地区进行格式化。
- **颜色具有强烈的文化特定含义**——如白色在某些地区与死亡/悲伤相关，在另一些地区与纯洁/和平相关。
  **若用颜色传达信息，须确保每个版本中传达相同内容。**

## 二、隐私（Privacy）

### 最佳实践【强制】
1. **仅请求访问你实际需要的数据。**
   请求功能所需之外的更多数据、或在用户对功能表示感兴趣前请求，会让用户很难信任你的 App。
   **尽量细化许可请求，让用户精准控制自己的数据。**
2. **对 App 如何收集和使用用户数据保持透明。** 始终遵照用户选择使用「隐藏邮件地址」「邮件隐私保护」等系统功能。
3. **尽量在设备端处理数据**（可用 Apple 神经网络引擎与定制 CreateML 模型），
   避免与远程服务器之间耗时且有潜在风险的来回通信。
4. **采用系统定义的隐私保护措施并遵守安全保护最佳实践。**

### 请求权限
必须请求访问权限的类别：
- **个人数据**：位置、健康、财务、联系方式及其他可识别个人身份的信息
- **用户生成内容**：电子邮件、信息、日历数据、联系人、游戏信息、Apple Music 活动、音频/视频/照片
- **受保护的资源**：蓝牙外围设备、家庭自动化功能、无线局域网连接、本地网络
- **设备功能**：摄像头、麦克风
- **ARKit 数据**：手部跟踪、平面估算、图像锚定、世界跟踪（全空间的 visionOS App）
- **广告标识符**（用于 App 跟踪）

规则：
1. **仅在 App 明确需要访问数据或资源时才请求权限。**【强制】
   理想做法是**等到用户实际使用需要该权限的功能时再请求**（如用户对位置功能表示感兴趣后再用**位置按钮**提供共享方式）。
2. **避免在启动时请求权限，除非该数据或资源对 App 正常运行必不可少。**【强制】
   请求原因显而易见时用户不太会被打扰（导航 App 需要位置、visionOS 反弹球游戏需要访问四周信息）。
3. **撰写清晰的目的字符串（用途描述字符串）。**【强制】
   - 用**直截了当、具体、易于理解的完整短句**；
   - **句首字母大写**、**避免被动语态**、**以句号结尾**。

   | 反例 | 问题 |
   |---|---|
   | 「需要访问麦克风以提供更好的体验。」 | 被动句，理由模糊且未定义 |
   | 「打开麦克风访问。」 | 祈使句，未提供任何理由 |

   | 正例 | 优点 |
   |---|---|
   | 「该 App 会在夜间进行记录以检测鼾声。」 | 主动句，清晰描述如何以及为何收集 |

### 预提醒屏幕 / 窗口 / 视图
（适用于相机、麦克风、位置、通讯录、日历、跟踪的系统提醒前自定义视图）

1. **仅包括一个按钮，并清楚表明它会打开系统提醒。**【强制】
   若还包含一个不打开提醒的按钮，用户会觉得自己被操纵。
   **用「继续」或「下一步」命名该按钮**，而不是「允许」之类的词。
2. **不在自定义屏幕或窗口中包括额外操作。**【强制】
   不提供可绕过系统提醒就退出屏幕/窗口的方式（**不提供关闭或取消选项**）。

### 跟踪请求【强制】
- **切勿在系统提供的提醒前显示可能迷惑或误导用户的自定义屏幕或窗口。**
  以下设计**禁止使用，否则将被 App 审核拒绝**：
  - 为授权请求**提供奖励**（不能因用户授予权限而提供补偿，
    也不能在用户允许跟踪前保留功能或内容、或让 App 无法使用）；
  - 显示**看起来像请求**的屏幕或窗口；
  - 显示**提醒图像**；
  - 在提醒后面的屏幕上显示**注解**。

### 位置按钮
- 让用户在任务需要位置时授予**临时权限**，外观可随界面变化，且始终可立即识别为位置共享操作。
- **可自定义**：标题（从系统提供项中选，如「当前位置」「共享我当前的位置」）、实心/空心位置图形、
  背景色与图形/标题颜色、圆角半径。**其他视觉属性不可自定义。**
- ⚠️ 系统会提醒颜色对比度低或半透明度过高等问题，并据此**拒绝授予位置权限**。
  确保文字在所有可访问性文字大小与翻译后都完整显示不被截断。

### 保护数据【强制】
1. **避免仅依靠密码进行认证**——尽可能使用 **passkeys**；继续用密码则要求**双重认证**；
   为保护设备上保持登录的访问，使用生物识别认证（面容 ID、视控 ID、触控 ID）。
2. **将敏感信息储存在钥匙串中。**
3. **切勿将密码或其他安全内容储存在纯文本文件中**（即使有文件权限限制也不如加密钥匙串安全）。
4. **避免创造自定义认证方案**——优先用系统功能：passkeys、通过 Apple 登录、Password AutoFill。

### 平台差异
- **macOS**：使用有效的 **Developer ID** 给 App 签名；通过 **App 沙盒化**保护用户数据；
  **避免假设登录者的身份**（快速用户切换意味着同一系统上可能存在多个活跃用户）。
- **visionOS**：ARKit 算法（视觉暂留、世界映射、分割、抠图、环境光线）始终运行，
  但 **ARKit 不会将数据发送给共享空间中的 App**；要访问 ARKit API 必须打开**全空间**，
  且平面估算、场景重建、图像锚定、手部跟踪等功能**需要用户许可**。
  **相机访问方式不同**：后置相机提供空白输入（仅用于兼容），前置相机为空间自影像提供输入（需用户许可）。
  登陆 visionOS 的 iOS/iPadOS App 若包含需要访问相机的功能，应**移除该功能**或替换为「让用户导入内容」。

## 三、从右到左（Right to Left）

系统提供的 UI 框架**默认支持 RTL**——使用系统组件与标准布局时，可能无需任何改动。
以下指南用于精细调整布局或适配特定地区的货币、数字与数学符号。

### 文本对齐
1. **若系统未自动调整，按界面对齐文本方向。** LTR 下左对齐的文本，RTL 下应右对齐以匹配内容的镜像位置。
2. **段落按语言对齐，而非按当前上下文。**【强制】
   - 段落定义为**三行及以上文本**；
   - 当段落对齐与其语言不匹配时，阅读会非常困难；
   - **一行和两行文本块**仍按**当前上下文**的阅读方向对齐，但**段落按语言对齐**。
3. **列表内所有文本项使用一致对齐**（包括以不同文字显示的项目）——混排对齐会造成阅读混乱。

### 数字与字符
- 不同 RTL 语言使用不同数字系统：**希伯来文用西方阿拉伯数字**；**阿拉伯文可能用西方或东方阿拉伯数字**
  （使用情况因国家、地区甚至同一国家内的区域而异）。
- **不要颠倒特定数字内部的顺序。**【强制】
  无论何种语言，具体数字（如 541、电话号码、信用卡号）的数位**顺序始终相同**。
- **对表示进度或计数方向的数字序列，颠倒序列顺序但不翻转数字本身。**【强制】
  进度条、滑块、评分控件中的数字需反向排列以匹配被翻转的控件方向。

### 控件
1. **翻转表示从一个值到另一个值进度的控件。**【强制】
   滑块、进度指示符需在 RTL 下翻转，同时**反转描述起止值的手势图标或图像的位置**。
2. **翻转帮助用户按固定顺序导览或访问项目的控件。**【强制】
   RTL 下返回按钮必须**指向右侧**，以匹配 RTL 语言的阅读顺序；下一个/上一个按钮同理。
3. **保持指向实际方向或指向屏上区域的控件方向不变。**【强制】
   表示「向右」的控件**必须始终指向右**。
4. **相邻的拉丁文与 RTL 文字需视觉平衡**：阿拉伯文/希伯来文没有大写字母，
   与全大写拉丁文并排时显得太小 → **将 RTL 文字字号增加约 2 点**。

### 图像
1. **避免翻转照片、插图和通用艺术作品。**【强制】
   翻转常会改变图像含义；翻转受版权保护的图像可能构成侵权。
   若图像内容与阅读方向强相关，**考虑创建新版本**而非翻转原图。
2. **当图像顺序有意义时，反转其位置**（时间顺序、字母顺序、喜爱程度等）。

### 界面图标
1. **翻转表示文本或阅读方向的图标**（如用左对齐横线表示文本 → RTL 下改为右对齐横线）。
2. **考虑为显示文本的图标创建本地化版本**（字号选择、签名等概念性文字）。
   若图标中的字母/词与阅读写作无关，考虑设计**不使用文本**的替代图像。
3. **翻转表示前进或后退运动的图标**——人们把与阅读方向一致的运动理解为「前进」。
   例：扬声器符号的声波在 LTR 下从左发出，RTL 下须翻转。
4. **不要翻转标志或通用符号与标记。**【强制】
   显示翻转的标志会让人困惑，可能引发法律后果；勾选标记等通用符号应保持外观一致。
5. **一般避免翻转描绘现实物体的图标**——时钟在各地运行方式相同，右手工具也无需翻转。
6. **翻转复杂的自定义图标前，先考虑其各组成部分与整体视觉平衡。**
   - 有些组件须遵循视觉设计语言（SF Symbols 在 LTR/RTL 下都用**同一反斜杠**表示禁止或否定）；
   - 有些组件的**位置**需翻转（角标代表 App 中实际 UI 时）；
   - 含手别暗示的组件（工具），考虑保留工具方向而必要时翻转基础图像。
